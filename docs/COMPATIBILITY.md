# Contract compatibility

The generic ingestion path accepts Soroban contract events from a configured contract ID and optional first-topic XDR filter. The RPC filter sends `[firstTopicXdr, "**"]`, following the [Stellar getEvents topic-filter syntax](https://developers.stellar.org/docs/data/apis/rpc/api-reference/methods/getEvents), so it matches events with additional topics. It preserves RPC event ID, network, epoch, transaction hash, ledger metadata, topic XDR, and value XDR. Decoder errors are retained with raw XDR and a coverage incident. A contract does not need to deploy the SoroPulse reference ticket contract to use generic delivery.

The optional `soropulse.ticket.v1` decoder matches [`soropulse-labs/contracts`](https://github.com/soropulse-labs/contracts) commit `34a2beb2bc9f189e3c0d25023b90ea5a54132cc6`. It expects `created`, `ticket`, and `closed` symbols as the first topic, version `U32(1)` as the second, and `U64(event_id)` as the third. `ticket` has fourth topic `U64(reservation_id)`. Business u64 IDs are decimal strings in JSON. The checked-in fixture in `fixtures/contract-v1/` was generated by that contract's Rust test harness with Soroban SDK 28.0.0 and is not a testnet capture. The contract manifest names testnet contract `CAUKWP7TRYYXAF2C5NDAZEAQVWCUMXX76KBPK64MQBZHU7EUJ5JVPHGG`; this backend has not verified that deployment live.

For the ticket consumer, filter by the configured contract ID and the XDR encoding of `Symbol("ticket")`. Preserve the blockchain event ID separately from the contract's business event ID and reservation ID. A schema-breaking topic order or data type change needs a new decoder and webhook schema decision; never reinterpret stored raw events silently.
