# Isolated consumer failure lab

The example ticket consumer has a development-only failure lab. It is disabled when `NODE_ENV=production` and requires the server-held `DEMO_API_KEY` in `X-Demo-Key`. `POST /demo/lab-sessions` accepts `scenario`, `budget` (1–3), and `ttl_seconds` (30–900), and returns a one-time `lab_` token and session ID. `GET /demo/lab-sessions/:id` reports scenario, budget, use count, and expiry. The token is stored as a hash in the consumer database.

Supported scenarios are `http_503`, `timeout`, `duplicate`, and `commit_drop`. A signed ticket webhook can include `lab: {session_id, token}` to activate a session. The token travels inside the HMAC-protected body. A valid session increments its use count atomically until the budget is exhausted; later deliveries process normally. The 503 scenario rejects before inbox persistence. Timeout delays the response for 11 seconds. Duplicate is a normal delivery used to inspect the consumer's stable-event deduplication. Commit-drop persists the inbox, synchronously processes that entry, then closes the response connection so a sender may retry after the business action commits. Sessions expire after at most 15 minutes.

The local PostgreSQL integration test verifies one `http_503` attempt followed by a successful retry, and confirms the consumer still has one ticket. The timeout and commit-drop scenarios have not yet passed automated tests. This lab is currently a consumer-side demonstration; the backend control-plane lab session API and machine-readable cross-service results are still pending. Never point these scenarios at arbitrary registered endpoints.
